# Repair Spotify matching from scratch-run evidence

## Problem and scope

The Spotify-only scratch run imported 394 likes. At the review snapshot 112 had downloaded and 46 needed attention, all at matching. Read-only catalog replay reproduced those 46 failures. Raw diagnostics are in `/tmp/lms-failure-review`, with a per-song report and official native artist-page names. This repair is part of the unmerged `feature/spotify-liked-songs` branch; the eventual PR includes that full feature relative to `origin/master`.

Correct false rejections while preserving the product rule: Spotify audio must come from a confidently identified, available YouTube Music Release Track. No video fallback or accepting duration alone. Existing library recording joins and release-level catalog identity must remain intact. Missing library-folder Activity copy is also already corrected in the uncommitted diff.

## Proposed implementation

1. **Artist aliases backed by the catalog.** Keep the current artist gate for ordinary matching. In a fallback pass, permit exact normalized equality against a candidate channel's Japanese official artist-page name, or exact equivalence of reordered whitespace-delimited credit-name tokens, retaining multiplicity. No fuzzy alias comparison or arbitrary token overlap. A candidate using either form of relaxed artist evidence must also have an exact normalized narrow title variant, not a substring similarity. Read Japanese pages only, in the song-search path, with a cap of three new channels per Spotify lookup. Cache promises per matcher run, evict rejected promises, and never retain an abort. Missing channel IDs provide no evidence. Shape errors and HTTP 404/410 provide no alias; propagate cancellation and transient errors only during this fallback pass. Leave album-first artist validation unchanged.

2. **Evidence for title differences.** Compare narrow bilingual title variants separated by ` - ` on both sides, rather than treating the whole translated title as one string. Keep recording-version checks on the full original titles and albums in both directions. Do not split `_` or strip recording-version labels from title variants. In the fallback pass only, when the original primary-artist gate and duration agree but title does not, reuse at most three public YouTube original-title reads per lookup. An original title must exactly agree with a narrow source variant. Preserve that evidence keyed by video ID and apply it at final release validation only if the browsed track's video ID equals the search result's. Treat oEmbed HTTP 4xx and shape errors as missing evidence; propagate aborts and transient errors in the fallback pass. Each admitted candidate may use at most one relaxed signal: artist alias/token order or original-title evidence, never both. Do not infer identity from album position plus duration or add a transliteration dependency. Some phonetic or translated titles remain unresolved without stronger evidence.

3. **Fallback ordering and selection.** Run the alias, token-order and original-title evidence pass only if ordinary album-first and song-search validation produces zero available release-member candidates. A valid ordinary match or an ordinary ambiguity must not trigger optional evidence reads. Keep the current numerical gates and 0.04 runner-up margin. Among compatible candidates inside that margin of the numerical leader, prefer exact normalized unstripped album name, then exact title/narrow variant. Accept a preference only if exactly one catalog video is on top; equally strong different IDs remain ambiguous. Use the same preference when selecting the release appearance of a single catalog video. This resolves HONEY's differing title-label punctuation through its exact album name. No Boy No Cry's album-version suffix must not count as an exact variant of the single. Do not merge different video IDs merely because metadata looks similar.

4. **Use the same evidence in saved-library matching.** Keep the synchronous scoring entrypoint for existing tracks, supplying already stored native artist names when present, with the same exact-title and single-relaxation rule. Load a channel-to-native-name map once per existing-library lookup rather than querying per track credit. Try ordinary evidence first and relaxed evidence only if none qualify. Network evidence remains inside the async matcher. Prefer exact edition/title among compatible existing tracks without weakening the rule that existing duplicates may satisfy a like. Do not add automatic rematching or timed retries for permanent failures.

5. **Failures and complexity.** Make ambiguity text say that multiple compatible Release Tracks were found, rather than claiming the song was absent. If cheap to preserve from lookup facts, distinguish catalog-marked unavailable candidates from no candidate; avoid a new diagnostics framework or schema migration. Use the existing matcher/catalog interfaces and helpers. Move Spotify-specific resolver code into a focused file only if it reduces complexity; avoid an additional public configuration surface.

Fuzzy alias substrings and alias-plus-original-title combinations must fail.
- Regression tests for bilingual title variants, original-title evidence, unavailable release membership, same-duration different songs, and preserved symmetric live/remix/cover/instrumental/version gates.
- Selection tests for the five L'Arc-en-Ciel original/remaster cases, Svefn-g-englar original/deluxe, Laputa/ROT, No Boy No Cry single/album-version, and continued ambiguity for Party!!, Bakaneji, ヘッドライト花火 and genuinely distinct equally strong recordings. Do not globally lower thresholds.

Take a read-only SQLite backup of the scratch database and replay already matched Spotify likes too, recording identity changes and inspecting each changed winner. - Run lint, all typechecks, and the complete test suite. Open the full Spotify feature PR, then fresh Claude Opus 5.5 and Codex adversarial reviews. Fix material findings and repeat within the review workflow. Merge only after Claude explicitly approves the final commit and required CI is green.

## Plan review responses

Claude Opus 5.5 round 1 rejected the initial draft. All six substantive findings and both simplifications were accepted: exact relaxed evidence instead of fuzzy aliases, fallback-only optional reads, video-ID-bound title evidence, explicit album/title ranking, validation of existing successes and named negatives, a single native-name map for saved-library scoring, no album-first alias reads, and Japanese-only artist pages. Round 2 explicitly approved the amended draft with two binding constraints: narrow title variants cannot gain substring credit, and native-page lookups must filter duration, version and exact title before reading.

Codex implementation round 1 found three further gaps, all accepted and fixed. Bilingual containment can also occur in the full label, so comparisons involving a split label now exclude substring credit for the full label too. Version, edition, mix and recording suffixes cannot produce exact bilingual variants. When an existing Standalone Recording acquires proven release membership, its contributions and audio file are reused while its Match is upgraded to that Release Track instead of dropping the new release evidence.

Claude's implementation round 1 also rejected bare whole-title containment: "Stay" and "Stay With Me" can be different songs. Spotify title scoring now uses the sequence ratio for bare extra words and retains containment credit only for an entire bracketed or spaced-dash suffix. Bilingual fragments still cannot gain substring credit. Saved-library reuse requires an exact narrow title and passes through the same Recording collapse, margin and ambiguity rule as catalog candidates; uncertain metadata falls through to a fresh catalog lookup. Reuse by a proven catalog video still prevents duplicate downloads afterwards. A second generation bump and token invalidation after sign-out storage clearing prevent concurrent refreshes from resurrecting the old Spotify session. All findings were accepted.

CodeRabbit's album-name "live" false positive and invalid `likedOn` route values were accepted and fixed. The requested account-scoped stale query was rejected because it conflicts with the existing single-selected-account behavior: old likes stay active until a complete replacement-account snapshot succeeds, then the replacement becomes authoritative. The shared transaction already implements this for both providers; an added Spotify account-switch regression locks it down. The migration's column order is correct and immutable, the concrete session refresh catches its errors, and speculative concurrent token-cache changes were declined to keep the implementation simple.

Implementation round 2 found three further gaps, all accepted. Narrow variants now require exactly one of the dash-separated labels to contain non-Latin letters, apart from labels that repeat the identical normalized title. That stops same-script metadata suffixes from masquerading as translations. Reprise, intro/interlude/prelude, bonus-track and numbered-part labels have an additional symmetric section check; merely removing their exact-title flag would leave ordinary suffix containment able to accept the wrong song. Version/edition labels in either bilingual segment disable splitting, rather than only checking the second segment. Exact album names "Live" and "LIVE!" now carry a live marker while studio-name regressions stay compatible. The identical-label exception preserves the real catalog's "LET IT DIE（OAO） - LET IT DIE (OAO)" without broad same-script splitting; normalization permits spacing before parentheses and Unicode width differences. Its regression was added after the successful-source replay exposed the changed album choice.

The optional Standalone-to-Release metadata upgrade can be replaced by a later Refresh if the higher-priority YouTube liked source still resolves as Standalone. Audio deduplication remains intact. That non-blocking limitation is retained and disclosed in the PR description. The revised head still requires a fresh final review.

Claude approved implementation round 3. Codex found one remaining false rejection: candidates already incompatible by recording section could consume the three optional title or native-name reads before a valid candidate. After the user requested continuation, the same section helper was applied before either optional read. Two full-matcher regressions fail on the prior head and pass with the fix, confirming rejected sections cannot exhaust either budget. Ordinary candidate scoring is unchanged. The complete suite passes with 525 tests and two skipped, plus lint, all typechecks and the production build. Fresh review of this revised head remains required before merge.
