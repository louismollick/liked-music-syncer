# Spotify Liked Songs research

Research date: 2026-10-04. Read-only inspection of liked-music-syncer and six shallow GitHub checkouts. All research outputs are under `/tmp/spotify-research`. The clones already existed when this research turn began; their origin URLs and shallow status were verified. Citations below link to the inspected commit, with repository-relative file names and line numbers. Recommendations are proposals, not implemented changes.

## Findings at a glance

| Repository | Reads private Liked Songs without your developer app? | Spotify access | Matching relevant to this app |
|---|---|---|---|
| SongMirror | Yes, cookie mode explicitly supports Free | `sp_dc` → web bearer via spotify_scraper → Pathfinder `fetchLibraryTracks` | Conservative recording/version gates; songs then videos; no YTM ISRC query in its own target |
| music-liked-sync | Yes, browser-session approach; no Premium check in path | Browser captures bearer, client-token, app version and query hashes → Pathfinder | One songs query; simple score; destructive version normalization |
| Stash | Yes, web-session approach; no Premium check in path | `sp_dc` + TOTP → bearer and client-token → Pathfinder | Album-first with cache; fallback search, scorer and player verification |
| Sunnify | No private library reader | Anonymous public embed pages and spclient playlist endpoint | Generic YouTube search, title/artist gates and nearest duration |
| spotDL | Its saved-library path uses official user OAuth | Default public metadata is SpotipyFree; `--user-auth` forces official Spotipy | Actual YTM ISRC search; songs then videos; several unsafe shortcuts |
| tunes | No private library reader | Anonymous public embed pages | Unfiltered YTM search via yt-dlp; title plausibility and album-tag preference |

The Premium restriction concerns the owner of a Development Mode app. Spotify's current [migration guide](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide) states that the app owner needs an active Premium subscription. A public downloader working without a Spotify account does not imply that it can read private Liked Songs.

## Current app baseline

`searchCandidate` produces up to six distinct `title artist` queries from `artistTitleIdentities`, searches songs with `ignoreSpelling: false`, takes up to 20 results per query, and deduplicates by video ID. It requires a candidate album browseId, title/artist identity gates, duration tolerance of 45 seconds or 60 for an original OMV, and `versionCompatible`. It ranks lexicographically by title ≥ .96, artist evidence, title, ATV status, duration difference, then whether the video differs from the source. It returns null for an exact tie on the first three criteria only when the top title is below .96. [app/src/main/match/resolve.ts:181-319](/Users/louismollick/code/liked-music-syncer/src/main/match/resolve.ts:181)

The identity gates are `title ≥ .96 && artist ≥ .88` or `title ≥ .88 && artist ≥ .82`. The normalizer preserves Unicode. Version markers cover live, remix, instrumental, sped up, slowed and others. However, `versionCompatible` is one-sided: a source without version markers accepts any candidate version; a source with markers checks only that its markers occur in the candidate title/album. It does not distinguish two named remixes. [app/src/main/match/text.ts:146-205](/Users/louismollick/code/liked-music-syncer/src/main/match/text.ts:146)

`likedContribution` first resolves the YTM like through its watch album, then falls back to song search, watches the selected candidate and browses its release. `releaseTrack` derives identity from the **actual release browseId and track videoId**. No match falls back to a standalone YTM video. Spotify has no source video to use for that fallback. [app/src/main/match/resolve.ts:41-110](/Users/louismollick/code/liked-music-syncer/src/main/match/resolve.ts:41) [app/src/main/match/resolve.ts:320-368](/Users/louismollick/code/liked-music-syncer/src/main/match/resolve.ts:320)

The Spotify lyrics client already fetches server time, generates TOTP with a rotating remotely fetched secret, requests `/api/token`, caches expiry, and uses `searchDesktop` Pathfinder. It sends no `sp_dc` cookie and its token path is anonymous. Reuse the token-generation mechanics, but a separate authenticated session is necessary for private likes. [app/src/main/lyrics/spotify.ts:12-42](/Users/louismollick/code/liked-music-syncer/src/main/lyrics/spotify.ts:12) [app/src/main/lyrics/spotify.ts:119-194](/Users/louismollick/code/liked-music-syncer/src/main/lyrics/spotify.ts:119) [app/src/main/lyrics/spotify.ts:201-260](/Users/louismollick/code/liked-music-syncer/src/main/lyrics/spotify.ts:201)

## 1. ahnafnafee/songmirror

### Spotify authentication and library reads

Cookie mode explicitly needs neither a developer Client ID/secret nor Premium. It delegates `sp_dc` token generation, including TOTP, to `spotify_scraper.auth.cookies.CookieTokenProvider`. It posts bearer-authenticated persisted queries to `https://api-partner.spotify.com/pathfinder/v2/query`, with WebPlayer headers, app version and browser User-Agent. An official OAuth implementation also exists, but it is a separate route requiring configured client credentials. [songmirror/songmirror/engine/spotify_cookie.py:1-20](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/spotify_cookie.py#L1-L20) [songmirror/songmirror/engine/spotify_cookie.py:141-169](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/spotify_cookie.py#L141-L169) [songmirror/songmirror/engine/spotify.py:165-175](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/spotify.py#L165-L175)

`favorite_tracks` requests `fetchLibraryTracks` with offset and limit 50, reads `data.me.library.tracks`, and requires `totalCount`. It fails if a page empties before the declared total. Offset advances by raw item count, before normalization. This matters when local/unavailable entries are skipped. The parser preserves `addedAt.isoString`, title, artist names, album name, `trackNumber`, duration and artwork. It initializes ISRC to null. [songmirror/songmirror/engine/spotify_cookie.py:648-692](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/spotify_cookie.py#L648-L692) [songmirror/songmirror/engine/spotify_cookie.py:742-763](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/spotify_cookie.py#L742-L763)

The author reports heavy throttling of the first-party bearer on REST `/me/tracks`; native Pathfinder avoids that REST bucket. Query hashes rotate with web releases. The implementation invalidates a token on 401 and re-scrapes the web-player JS on `PersistedQueryNotFound`. Network retries are bounded for reads. HTTP 429 otherwise surfaces through `raise_for_status`; the liked-reader does not implement a specific Retry-After loop. These are source-code claims and behavior, not a live authenticated validation in this research. [songmirror/songmirror/engine/spotify_cookie.py:180-259](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/spotify_cookie.py#L180-L259) [songmirror/songmirror/engine/spotify_cookie.py:742-746](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/spotify_cookie.py#L742-L746)

Cookie-only reconciliation intentionally permits missing ISRCs. Opting into `require_isrc` calls official catalog lookups, including a single-track fallback with an author-reported roughly 300/day development-app budget. Thus its ISRC enrichment is **not** a complete no-developer-app solution. The claim that ISRC is absent from the entire web-player surface is the author's comment; the directly demonstrated fact is that these parsers do not obtain it. [songmirror/songmirror/engine/spotify_cookie.py:695-739](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/spotify_cookie.py#L695-L739) [songmirror/songmirror/engine/spotify_cookie.py:620-645](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/spotify_cookie.py#L620-L645)

### Spotify → YouTube Music matching

Its own YTM target searches `track name + primary artist`, then a romanized variation when different. Per query it tries `filter="songs"`, limit 8, then `videos` only when no song passes. It returns the highest acceptable score within the first successful query/filter. No album-first lookup or album scoring occurs in this path; no direct YTM ISRC search or MusicBrainz recording lookup occurs here. The broad README ISRC hierarchy describes multi-provider matching, not an ISRC query in this target. [songmirror/songmirror/engine/targets/ytmusic.py:854-865](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/targets/ytmusic.py#L854-L865) [songmirror/songmirror/engine/targets/ytmusic.py:956-989](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/targets/ytmusic.py#L956-L989)

Score is `.45 title + .35 artist + .20 duration`. Duration score is `max(0, 1 - deltaMs/10000)`, unknown duration .5. Within 2.5 seconds it allows the better of strict and loose title scores; otherwise only strict. Acceptance is close duration plus title ≥ .78 and artist ≥ .92, or strict title ≥ .88 and artist ≥ .92. Independent metadata compatibility gates run first, including artist ≥ .92 and a hard five-second duration tolerance when both positive durations are known. [songmirror/songmirror/engine/matching.py:21-23](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/matching.py#L21-L23) [songmirror/songmirror/engine/matching.py:407-469](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/matching.py#L407-L469)

Version handling is stronger than ours. It compares symmetric recording signatures, including marker families and named qualifiers for mixes/venues/version numbers, and reconciles featured credits. Families include live, remix/rework, instrumental, karaoke, acoustic, edit, extended speed variants, cover, mono/stereo and re-recording. Catalog decorations such as remaster/clean/explicit can be normalized separately. There is no runner-up margin; equal scores keep the first result. Misses return null and are cached. [songmirror/songmirror/engine/matching.py:30-64](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/matching.py#L30-L64) [songmirror/songmirror/engine/matching.py:178-222](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/matching.py#L178-L222) [songmirror/songmirror/engine/matching.py:248-284](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/matching.py#L248-L284) [songmirror/songmirror/engine/targets/ytmusic.py:854-865](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/targets/ytmusic.py#L854-L865) [songmirror/songmirror/engine/targets/ytmusic.py:976-989](https://github.com/ahnafnafee/songmirror/blob/de7fab3fe8ef347384bf2989b01e4e9d72c2b4b8/songmirror/engine/targets/ytmusic.py#L976-L989)

Borrow the complete-pagination guard, lazy hash refresh, Unicode/romanized discovery and symmetric version signatures. Its video fallback and video-ID-only result are worse for our release-identity requirement. Its hard five-second duration gate is useful for Spotify recordings. Its permissive treatment of remaster/clean/explicit decorations needs care for our release and explicit-version identity policy.

## 2. rabilrbl/music-liked-sync

### Spotify authentication and library reads

A persistent browser session requires `sp_dc`. Rather than generating TOTP itself, it loads Spotify's real web app and captures `/api/token` responses and outgoing Pathfinder requests. It rejects `isAnonymous: true`, captures `client-token` and `spotify-app-version`, and discovers persisted hashes by navigating to `/collection/tracks` and a search page. Thus the browser handles Spotify's current token protocol. No official OAuth app or Premium requirement is coded into this path; Free compatibility is an inference from first-party web login, not an account test performed here. [music-liked-sync/src/music_liked_sync/constants.py:16-23](https://github.com/rabilrbl/music-liked-sync/blob/0c5241ed9339f9e12878df97a2e2ed8426ea5520/src/music_liked_sync/constants.py#L16-L23) [music-liked-sync/src/music_liked_sync/spotify.py:45-166](https://github.com/rabilrbl/music-liked-sync/blob/0c5241ed9339f9e12878df97a2e2ed8426ea5520/src/music_liked_sync/spotify.py#L45-L166)

The adapter's misleadingly familiar `current_user_saved_tracks` name wraps Pathfinder `fetchLibraryTracks`, not REST `/v1/me/tracks`. It parses `data.me.library.tracks`, title, artist, duration and album name, but drops added_at and does not expose ISRC, album type, track number or explicit. Its track duration parser reads `duration`, while SongMirror/Stash support both `duration` and `trackDuration`. [music-liked-sync/src/music_liked_sync/_spotify_client.py:99-145](https://github.com/rabilrbl/music-liked-sync/blob/0c5241ed9339f9e12878df97a2e2ed8426ea5520/src/music_liked_sync/_spotify_client.py#L99-L145) [music-liked-sync/src/music_liked_sync/_spotify_client.py:269-278](https://github.com/rabilrbl/music-liked-sync/blob/0c5241ed9339f9e12878df97a2e2ed8426ea5520/src/music_liked_sync/_spotify_client.py#L269-L278)

On 401 or a persisted-query error it rebuilds browser-derived state once and retries. Retry helpers cover 429 and 500/502/503/504. `Retry-After` is capped at 30 seconds, with five attempts. A long server-directed wait should be preserved in our app rather than truncated to 30 seconds. [music-liked-sync/src/music_liked_sync/_spotify_client.py:154-205](https://github.com/rabilrbl/music-liked-sync/blob/0c5241ed9339f9e12878df97a2e2ed8426ea5520/src/music_liked_sync/_spotify_client.py#L154-L205) [music-liked-sync/src/music_liked_sync/_spotify_client.py:245-267](https://github.com/rabilrbl/music-liked-sync/blob/0c5241ed9339f9e12878df97a2e2ed8426ea5520/src/music_liked_sync/_spotify_client.py#L245-L267) [music-liked-sync/src/music_liked_sync/constants.py:33-36](https://github.com/rabilrbl/music-liked-sync/blob/0c5241ed9339f9e12878df97a2e2ed8426ea5520/src/music_liked_sync/constants.py#L33-L36)

### Matching

Spotify → YTM uses only `wanted.title + all artists`, `filter="songs"`, default limit 5. The many query variants in `build_spotify_search_queries` are for the reverse direction, YTM → Spotify. It does not search YTM by album or ISRC, browse album tracklists, or consult MusicBrainz. [music-liked-sync/src/music_liked_sync/ytmusic.py:254-261](https://github.com/rabilrbl/music-liked-sync/blob/0c5241ed9339f9e12878df97a2e2ed8426ea5520/src/music_liked_sync/ytmusic.py#L254-L261) [music-liked-sync/src/music_liked_sync/spotify.py:169-195](https://github.com/rabilrbl/music-liked-sync/blob/0c5241ed9339f9e12878df97a2e2ed8426ea5520/src/music_liked_sync/spotify.py#L169-L195) [music-liked-sync/src/music_liked_sync/spotify.py:273-292](https://github.com/rabilrbl/music-liked-sync/blob/0c5241ed9339f9e12878df97a2e2ed8426ea5520/src/music_liked_sync/spotify.py#L273-L292)

It first returns a candidate with an identical normalized title/artist key, bypassing duration. Otherwise score is `.62 SequenceMatcher(title) + .33 binaryArtistMatch + .05 max(0,1-deltaMs/30000)`, accepted ≥ .82 with an artist match. Artist matching allows equality, containment or similarity ≥ .86. It has no album score, hard duration limit or tie-margin rejection. Search failures and ordinary misses are recorded separately; misses remain unmatched. [music-liked-sync/src/music_liked_sync/utils.py:77-114](https://github.com/rabilrbl/music-liked-sync/blob/0c5241ed9339f9e12878df97a2e2ed8426ea5520/src/music_liked_sync/utils.py#L77-L114) [music-liked-sync/src/music_liked_sync/sync.py:120-145](https://github.com/rabilrbl/music-liked-sync/blob/0c5241ed9339f9e12878df97a2e2ed8426ea5520/src/music_liked_sync/sync.py#L120-L145)

The normalizer removes all bracketed text, common suffixes including live/radio edit, and every non-ASCII letter. That can collapse versions and erase CJK titles. It is clearly worse than our Unicode preservation and version-aware matching. Borrow browser capture of real tokens/headers/hashes if direct cookie TOTP proves fragile, and separation of search failure from no-match. Do not borrow its normalization or exact-key bypass. [music-liked-sync/src/music_liked_sync/utils.py:15-63](https://github.com/rabilrbl/music-liked-sync/blob/0c5241ed9339f9e12878df97a2e2ed8426ea5520/src/music_liked_sync/utils.py#L15-L63) [music-liked-sync/src/music_liked_sync/constants.py:3-9](https://github.com/rabilrbl/music-liked-sync/blob/0c5241ed9339f9e12878df97a2e2ed8426ea5520/src/music_liked_sync/constants.py#L3-L9)

### Matching

Album matching runs first when the Spotify album is nonblank. It searches `artist album`, then `artist albumWithoutParentheticalSuffixes`, using unfiltered InnerTube search and extracting album browse IDs from album cards/shelves/flat rows. Album title threshold is .80 plus artist subtitle validation. It browses the album tracklist and caches both successes and misses by lowercased `artist|album`, with 200-entry LRU capacity. [Stash/data/download/src/main/kotlin/com/stash/data/download/DownloadManager.kt:771-801](https://github.com/rawnaldclark/Stash/blob/1a37fdc7ee655f9e9d38e5c193c988e9ab976a5d/data/download/src/main/kotlin/com/stash/data/download/DownloadManager.kt#L771-L801) [Stash/data/download/src/main/kotlin/com/stash/data/download/matching/AlbumMatchExecutor.kt:33-83](https://github.com/rawnaldclark/Stash/blob/1a37fdc7ee655f9e9d38e5c193c988e9ab976a5d/data/download/src/main/kotlin/com/stash/data/download/matching/AlbumMatchExecutor.kt#L33-L83) [Stash/data/download/src/main/kotlin/com/stash/data/download/matching/AlbumMatchExecutor.kt:172-263](https://github.com/rawnaldclark/Stash/blob/1a37fdc7ee655f9e9d38e5c193c988e9ab976a5d/data/download/src/main/kotlin/com/stash/data/download/matching/AlbumMatchExecutor.kt#L172-L263)

Within the album, Jaro-Winkler over canonical titles must be ≥ .85 within 5 seconds; fallback ≥ .70 within 3 seconds. ## Synthesis

### Best supported private-library route without a developer app

Use a signed-in web-player session: **`sp_dc` + current TOTP → authenticated bearer → Pathfinder `fetchLibraryTracks`**. SongMirror, music-liked-sync and Stash independently implement the same library query; SongMirror explicitly says Free works. ### Recommended matching algorithm for liked-music-syncer

These starting thresholds are deliberately conservative proposals. Validate them against a labeled sample before loosening them. They are not empirically calibrated by this research.

1. **Use existing local YTM evidence first.** Look up an existing Spotify-ID mapping to a validated YTM release track. For a new Spotify like, compare against already resolved YTM likes/catalog tracks with the same gates below. If exactly one compatible existing release identity survives, reuse it. This is essential because Spotify and YTM can list the same recording on different single/album/compilation releases.
2. **Try the Spotify album once per album ID.** Query `albumName albumPrimaryArtist`, `filter="albums"`, up to five results. This needs a small new catalog search method; the present interface only has `searchSongs`. Use the album's artist when known, otherwise the track's primary artist. Retry a decoration-only cleaned album title once, preserving live/remix edition meaning. Require album-title similarity ≥ .90 and artist ≥ .88; inspect at most the top three qualifying releases. Browse their structured tracklists and cache them by Spotify album ID. Track/disc number may locate candidates, but must never override title/artist/duration checks.
3. **Use the existing song-search machinery for fallback.** In order: original `title primaryArtist albumName`, original `title primaryArtist`, title with only feature/catalog decorations removed plus primary artist, then original title with another credited artist. Deduplicate normalized queries and cap at six, with 20 results each. Use `filter="songs"`, `ignoreSpelling: false`. Keep named version terms in every query where possible. Search all required variants before choosing an ambiguous winner; stop early only for a unique high-confidence result on a validated exact release.
4. **If ISRC is actually known**, try raw ISRC once before the text-song fallback, with the songs filter and spelling correction disabled. Treat the returned rows as candidates and apply the same metadata gates. Do not trust one song result solely because the query looked like an ISRC. Do not fetch ISRCs through borrowed client credentials.
5. **Do not auto-accept a video-only result.** The required output is a Release Track. Videos can be a later manual discovery aid, but unresolved Spotify rows should remain unresolved. Do not invent a videoId from a Spotify ID or invoke `likedContribution` with a fake YTM like.

Use these hard gates before scoring:

- Actual usable `videoId` and album `browseId`; track must exist in the browsed release and be available.
- Keep `textSimilarity`, `normalizeText`, artist identity variants and current `identityScoresMatch` as reusable building blocks. For automatic Spotify matching, require **T ≥ .90 and A ≥ .88**, with stricter normal acceptance below. Compare primary artist independently; corroborate remaining credits without joining every artist into one giant fuzzy string.
- Known durations must differ by **≤5 seconds**. Spotify durations describe recordings, so our YTM-video tolerances of 45/60 seconds are inappropriate here. Unknown duration cannot get automatic acceptance until watch/release metadata fills it, or exact stored identity establishes the match.
- Make version compatibility symmetric. Reject live/studio, remix/original, instrumental/vocal, acoustic/electric, sped/slowed/original and cover/original conflicts. Compare named remixer/live venue/version qualifiers when supplied. Do not erase these terms to boost the title score. Use explicit title/album variant markers separately, to avoid treating a song literally named "Live" as a performance marker without context.
- Known explicit flags that disagree must not auto-merge. Missing explicit is unknown. Clean/explicit and radio/extended cuts can share most text and sometimes nearly identical durations.

A simple ranking proposal after those gates:

```text
T = textSimilarity(sourceTitle, candidateTitle), preserving meaningful version text
A = max similarity of source primary artist to candidate credited artists
L = album-title similarity, or 0.5 if unavailable
D = max(0, 1 - abs(durationDifferenceSeconds)/10), or 0.5 if unknown
S = 0.45*T + 0.30*A + 0.15*L + 0.10*D
```

No popularity score. Album mismatch is not automatically fatal, because a single and album can carry the same recording, but exact album/release evidence is useful for ranking. A valid ISRC search hit gets no unconditional score boost.

**Auto-accept:** T≥.96, A≥.88, known duration within 5 seconds, S≥.90, and runner-up gap ≥.04 across distinct release identities. For a verified exact-album result with L≥.96, allow T≥.90 only when A≥.90, duration within 3 seconds and S≥.90, again with a ≥.04 gap. For short titles, require exact normalized title rather than containment. These thresholds favor a small unmatched queue over a silent wrong release.

**Ties:** collapse identical `(browseId, videoId)` candidates before computing the gap. Use already accepted YTM identity as the preferred canonical target when compatible. For otherwise equivalent alternate releases, prefer a unique verified Spotify-album match. If neither rule distinguishes them, leave unresolved with the two candidates. A deterministic videoId sort can stabilize display order, but must not turn ambiguity into evidence. An exact title does not justify bypassing ambiguity checks, as the current matcher sometimes does.

**Finalization:** browse the selected release, verify track membership, compare observed metadata again, and construct the existing `releaseTrack`/`releaseIdentityKey` result. Keep Spotify track ID, added_at and source membership separate from YTM `sourceVideoId`; refactor to a source-neutral matching input rather than making Spotify pretend to be `LikedSong`. Preserve unresolved source rows and distinguish no-match, ambiguity, authentication failure and network failure.

This can remain small: generalize candidate gathering/ranking inside `searchCandidate`, add a single album-search method only for the album-first step, reuse `catalog.release`, `catalog.watch`, `findReleaseTrack` and `releaseTrack`, and persist successful source-to-release mappings. Keep the existing YTM path's wider duration tolerance where the source is an OMV. ### Deduplication caveat worth resolving before implementation

The same recording can have multiple release browseIds and videoIds. Matching Spotify's exact album while the YTM like resolves to a single release will produce two release identities under the current scheme. ISRC identifies a recording, not necessarily a unique release-track identity. SongMirror's ISRC-level union is consequently not a drop-in replacement for our release-key deduplication.

Prefer a unique compatible already-resolved YTM contribution before external album search, and retain that canonical mapping. If neither source was previously resolved, use the same canonical-release preference for both source resolvers. Never merge different explicit/creative versions just to reduce duplicate rows. Guaranteeing deduplication across every alternate release would require a separate recording-equivalence policy, which is a larger product decision than adding Spotify as a source. This report recommends the local-first reuse above as the smallest practical improvement.
